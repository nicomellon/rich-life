# Backend

The Rich Life API: FastAPI and Pydantic, with SQLAlchemy 2.0 and Alembic on PostgreSQL (psycopg 3, synchronous). Dependencies are managed with [uv](https://docs.astral.sh/uv/).

## Running

From the repository root, `make setup` installs the dependencies and creates `.env`, then `make backend` starts the API. To do it by hand:

```sh
cd backend
uv sync
uv run --env-file ../.env alembic upgrade head
uv run --env-file ../.env uvicorn app.main:app --reload
```

- Health check: http://localhost:8000/health
- Interactive API docs: http://localhost:8000/docs

In production the API runs from the image built by `Dockerfile`. Its entrypoint, `docker-entrypoint.sh`, applies the migrations and then starts uvicorn on port 8000. See [docs/deployment.md](../docs/deployment.md).

## Configuration

Following the [twelve-factor](https://12factor.net/config) approach, `app/core/config.py` reads settings **only from environment variables**; the app never opens a `.env` file itself. For local development, `make backend` loads the root `.env` (the same one docker compose uses) into the environment with `uv run --env-file`. You can use any other tool for that instead, such as direnv or `UV_ENV_FILE=../.env`. In production, set real environment variables. See `.env.example` for the defaults.

| Variable | Required | Default |
|---|---|---|
| `APP_VERSION` | no | `dev` (set by the build or deploy pipeline, e.g. to a git tag or commit SHA) |
| `DATABASE_URL` | no | `postgresql+psycopg://richlife:richlife@localhost:5432/richlife` |
| `JWT_SECRET` | yes | none (at least 32 characters; generate one with `openssl rand -hex 32`) |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | no | `10080` (7 days; there are no refresh tokens yet) |
| `WEBAUTHN_RP_ID` | no | `localhost` (the domain the web app is served from; passkeys are bound to it) |
| `WEBAUTHN_RP_NAME` | no | `Rich Life` (shown in the browser's passkey prompts) |
| `WEBAUTHN_ORIGIN` | no | `http://localhost:5173` (the web app's origin) |
| `CORS_ORIGINS` | no | `http://localhost:5173` (comma-separated list) |
| `REDIS_URL` | no | `redis://localhost:6379/0` (holds magic-link tokens and rate-limit counts) |
| `EMAIL_DELIVERY` | no | `log` (writes sign-in links to the log); `resend` emails them through [Resend](https://resend.com) |
| `EMAIL_API_KEY` | with `resend` | none (Resend API key; the API refuses to start without it) |
| `EMAIL_FROM` | with `resend` | none (the sender, e.g. `Rich Life <sign-in@example.com>`, on a domain verified in Resend) |
| `MAGIC_LINK_EMAIL_LIMIT` | no | `3` (sign-in links one email address can ask for in 15 minutes) |
| `MAGIC_LINK_IP_LIMIT` | no | `20` (link requests, and link sign-ins, one IP can make in 15 minutes) |

## Database

`app/db/session.py` creates the engine from `DATABASE_URL` and provides `get_db`, a FastAPI dependency that opens one session per request. Route handlers take it as `db: DbSession` (from `app/api/deps.py`) and commit explicitly; anything left uncommitted is rolled back when the request ends.

Models subclass `Base` from `app/db/base.py` and must be imported in `app/models/__init__.py` so that Alembic sees them. Migrations live in `migrations/versions/`. Alembic is configured in `pyproject.toml` (`[tool.alembic]`) and reads the database URL from the app settings, so it uses the same `DATABASE_URL` as the API. With Postgres running (`make db`):

```sh
make migrate                              # alembic upgrade head
make migration m="add users table"        # alembic revision --autogenerate -m "..."
uv run --env-file ../.env alembic downgrade -1
```

Review every autogenerated migration before committing it: Alembic can't detect everything, such as renamed columns or some changes to types and server defaults.

### Example data

Accounts sign in with passkeys, so there is no shared demo account. To have something to look at, register an account in the app, then add three months of example data to it:

```sh
make seed email=you@example.com   # from the repository root
uv run --env-file ../.env python -m app.scripts.seed --email you@example.com
```

`app/scripts/seed.py` adds the current month and the two before it, with an income and entries in every bucket, using the account's current spending plan. The current month only gets the example entries dated up to today. It skips months the account already has, so running it again changes nothing.

| `app/models/` | SQLAlchemy models |
| `app/schemas/` | Pydantic request and response models |
| `app/services/` | Business logic, kept free of HTTP concerns |
| `app/scripts/` | Command-line scripts, e.g. the example data seed |
| `tests/` | pytest suite |

## Authentication

Users sign in with passkeys (WebAuthn, via [py_webauthn](https://github.com/duo-labs/py_webauthn)); there are no passwords. Each ceremony takes two calls: the web app asks for a challenge, passes the returned options to the browser (`navigator.credentials.create()` or `.get()`), and posts the browser's credential back to be verified.

| Step | Register | Sign in |
|---|---|---|
| 1. Get options | `POST /api/v1/auth/register-challenge` with `{email}` (409 if taken) | `POST /api/v1/auth/login-challenge` |
| 2. Verify | `POST /api/v1/auth/verify-registration` creates the user and passkey | `POST /api/v1/auth/verify-login` |

Both verify endpoints return a JWT access token signed with `JWT_SECRET`, or 401 if the credential doesn't verify. Challenges live in the `webauthn_challenges` table for 5 minutes and are deleted on first use, so each works once. Sign-in names no credentials, so the browser offers every passkey it has for the site and the user never types an email.

Called with a bearer token, `register-challenge` and `verify-registration` add a passkey to the signed-in account instead of creating one: the body of `register-challenge` is optional and its `email` is ignored, and `verify-registration` returns a fresh token. A challenge only works for the kind of registration it was issued for, and for the same account. A bearer token that is sent but invalid or expired gets 401.

### Magic links

Users without a passkey on their device can sign in with an emailed link:

1. `POST /api/v1/auth/magic-link` with `{email}` always responds 202 with no body, so it doesn't reveal which emails have accounts. If an account has the email, it emails a link to `{WEBAUTHN_ORIGIN}/sign-in/link#token=<token>`, where the token is 32 random bytes in base64url. Redis keeps only the token's SHA-256 hash, for 15 minutes. Asking again doesn't cancel earlier links.
2. `POST /api/v1/auth/magic-link/verify` with `{token}` deletes the token and returns an access token, so each link signs in once. Unknown, expired and used tokens get 401 `magic_link_invalid`.

Each email address can ask for 3 links, and each IP for 20, in any 15 minutes; each IP can also try 20 tokens. Over a limit, the API responds 429 `rate_limited` with a `Retry-After` header. With `EMAIL_DELIVERY=log`, the default for development, the email is written to the API's log instead of being sent.

Send the token as `Authorization: Bearer <token>`; in `/docs`, paste it into **Authorize**. You need a browser to get one, since `/docs` can't run a passkey ceremony. Protected routes take the user as `user: CurrentUser` (from `app/api/deps.py`), which responds 401 when the token is missing, invalid or expired.

## Checks

```sh
uv run pytest                  # tests
uv run ruff check .            # lint
uv run ruff format .           # format
uv run mypy                    # type check (strict)
```

The tests need Postgres and Redis (`make db`). They apply the migrations to the `DATABASE_URL` database, then run each test in a transaction that is rolled back afterwards, so they leave no data behind. They empty the Redis database before and after each test: by default database 1, apart from the development server's database 0, or whichever `REDIS_URL` names. Emails go to a fake sender (`tests/emails.py`) that keeps them for the tests to read. Passkey tests use a software authenticator (`tests/authenticator.py`) that creates real credentials and signatures, so the WebAuthn verification runs unmocked.

`make test` and `make lint` from the repository root run these along with the rest of the repository's checks.
